# Табличные части production XML

Цель: зафиксировать production-подход для XML 1110335 без ухода в compact-агрегацию, исходя из `nalog target.docx`, XSD и текущей модели формы.

## Ключевой вывод

**Compact-режим не обязателен по формату.**

`nalog target.docx` + XSD прямо допускают передачу табличной части подробно:

- `НаимИСт/ВидРаб` — `maxOccurs="unbounded"`
- `НаимИСт/Раздел` — `maxOccurs="unbounded"`
- `Раздел/СвВидРаб` — множественные строки внутри раздела

Следовательно, для production-документов правильная стратегия:

1. **Не агрегировать табличные части по умолчанию**
2. Передавать строки КС-2 максимально близко к исходной форме
3. Оставить compact только как fallback/debug profile, но не как основной сценарий

### `Раздел` (табл. 5.9)

| XML поле | Зачем | Откуда брать / как хранить |
|---|---|---|
| `НомСтр` | номер позиции раздела в общем перечне | генерировать по порядку |

| `НомРазд` | номер раздела в перечне работ | генерировать по порядку разделов |

## Production-подход для нескольких КС-2

Текущая модель уже допускает рост до нескольких листов `ks2Sheets`.

### Рекомендуемая схема XML

1. Все листы КС-2 складываются в **единый `НаимИСт`**.
2. Внутри него:
   - либо плоский список `ВидРаб`,
   - либо список `Раздел`, каждый со своими `СвВидРаб`.
3. Нумерация должна быть **сквозной по всем листам**:
   - `НомСтр` для `ВидРаб`
   - `НомСтр` / `НомРазд` для `Раздел`
4. Привязка к листу КС-2 должна сохраняться в модели, даже если в XML она не видна напрямую.

### Что для этого уже есть

- `ks2Sheets[]`
- `rows[]` со `section/item`
- `lineNo`
- `estimateNo`
- `quantity`
- `price`
- `amount`
- `unit`

### Что стоит добавить в модель на будущее

| Поле | Зачем |
|---|---|
| `sheetIndex` у XML-элементов | внутренний trace/debug |
| `sectionIndex` | сквозная нумерация разделов |
| `xmlRowNo` | стабильная сквозная нумерация |
| `xmlSectionNo` | отдельная нумерация разделов |

## Практическое решение на сейчас

### По умолчанию
- использовать **full / как в форме**
- compact считать только вспомогательным режимом

### Следующий этап доработки
1. Перевести генератор XML на production-default `full`
2. Формировать `Раздел` из section-строк КС-2
3. Формировать `СвВидРаб` из item-строк внутри каждого раздела
4. Добавить:
   - `НомСтр`
   - `НомРазд`
   - `ПозРаздСмет`
   - `ПозСмет`
   - `КолТов`
5. После этого прогонять full-profile по XSD и собирать, какие поля ещё реально нужны для Diadoc/Sch-проверок

## Вывод

Для production-документов правильный путь — **не уходить в compact**, а строить XML по полной табличной структуре, потому что:

- формат это позволяет;
- исходный Excel уже является официальной формой;
- бизнес-данные должны передаваться максимально полно;
- текущая модель формы уже почти готова к блоковому росту на несколько КС-2.
