# Сводка по передаче Excel-иерархии в XML

Дата: 2026-03-21

## Короткий вывод

Есть **две разные истории**:

1. **Табличная часть работ КС-2** (`НаимИСт / Раздел / СвВидРаб`) — иерархию передавать **можем**.
2. **Удержания / требования** (`СвОРасч / УчетТребУдерж`) — Excel-иерархию вида
   "строка-итог + несколько документов/подпунктов под ней" передавать **не можем в том же виде**.

Причина: формат `1110335` сам по себе заметно компактнее Excel именно в блоке `СвОРасч`.

---

## 1. Что можно передавать из Excel почти 1-в-1

| Excel-сущность | Куда ложится в XML | Сейчас в проекте | Комментарий |
|---|---|---|---|
| лист / раздел КС-2 | `НаимИСт/Раздел` | да | поддерживается |
| строки работ внутри раздела | `Раздел/СвВидРаб` | да | поддерживается |
| наименование работ | `СвВидРаб/@НаимТов` | да | поддерживается |
| сумма строки за период | `СвВидРаб/@СтТовБезНДС` | да | поддерживается |
| тип затрат | `СвВидРаб/@ТипЗатр` | да | поддерживается |
| единица измерения / количество | `ОКЕИ_Стройка`, `НаимЕдИзм`, `КолТов` | да / частично по сценарию | зависит от заполнения строки |
| суммы разделов | `Раздел/@СтБезНДСРаздОтч` и др. | да | поддерживается |
| полная табличная часть КС-2 | `Раздел + СвВидРаб` | да | уже зафиксировано как поддерживаемое |

### Вывод

**По работам и разделам XML умеет иерархию.**

То есть схема типа:
- раздел / название блока;
- внутри несколько строк работ;
- суммы по разделу;

— для блока `НаимИСт` **нормальна**.

---

## 2. Что можно передавать по удержаниям сейчас

| Excel / форма | XML | Сейчас в проекте | Статус |
|---|---|---|---|
| общая сумма удержаний | `СвОРасч/@СумУдержВсегоОтч` | передаётся | ок |
| общая сумма требований | `СвОРасч/@СумТребВсегоОтч` | передаётся | ок |
| сумма к оплате | `СвОРасч/@ВсегоКОплатОтч` | передаётся | ок |
| один вид требования/удержания | `СвОРасч/УчетТребУдерж/(ВидТреб или ВидУдерж)` | передаётся | ок |
| `ИнВидТреб` для кода `05` | `СвОРасч/УчетТребУдерж/ИнВидТреб` | передаётся | ок |
| `ИнВидУдерж` для кода `36` | `СвОРасч/УчетТребУдерж/ИнВидУдерж` | передаётся | ок |
| один подтверждающий документ | `СвОРасч/УчетТребУдерж/ДокПодтСумУд` | передаётся | ок |
| выбор основной XSD-ready строки | влияет на `УчетТребУдерж` | передаётся | ок |

### Что это означает

В `СвОРасч` сейчас реально живут:
- итоговые суммы,
- один агрегированный `УчетТребУдерж`,
- один выбранный вид (`ВидТреб` **или** `ВидУдерж`),
- при необходимости один supporting document.

---

## 3. Что из Excel-иерархии удержаний не помещается в XML напрямую

| Что есть в Excel | Можно ли передать 1-в-1 | Почему |
|---|---|---|
| несколько строк удержаний за период | нет | текущий `СвОРасч` у нас агрегированный |
| строка-итог по виду работ + под ней несколько документов удержаний | нет | в `СвОРасч` нет такой иерархической модели |
| несколько документов под одним удержанием | нет | в `СумТребУдержТип` только один `ДокПодтСумУд` |
| незакрытый остаток прошлого периода как отдельный реквизит | нет напрямую | в `СвОРасч` нет отдельного поля под Excel-модель |
| остаток к закрытию следующего периода | нет напрямую | прямого поля в `СвОРасч` нет |
| комментарии строк удержаний | по решению проекта не передаём | это не бизнес-узел XML |

### Главный вывод по твоему вопросу

Сценарий:
- есть строка с названием работ и общей суммой;
- под ней несколько документов удержаний;

**в блоке `СвОРасч` так собрать нельзя**.

Для удержаний XML `1110335` не даёт нам такую же вложенную структуру, как в Excel.

---

## 4. Почему именно нельзя

### 4.1. По проектным выводам

У нас уже зафиксировано:
- строки удержаний сейчас идут только частично и агрегированно;
- несколько строк удержаний/требований из Excel не передаются поштучно;
- multiple `УчетТребУдерж` в текущем рабочем профиле ломают XSD.

### 4.2. По XSD

В `СвОРасч` есть элемент `УчетТребУдерж`, и в текущей схеме он не описан как иерархический контейнер с дочерним списком документов.

Состав `СумТребУдержТип` такой:
- `ВидТреб` **или** `ВидУдерж`;
- `ИнВидТреб` **или** `ИнВидУдерж`;
- `ДокПодтСумУд` (один, optional);
- атрибут `СумТребУдерж`.

То есть это **одна запись суммы требования/удержания**, а не мини-таблица с подпунктами.

---

## 5. Практическое правило для интерфейса

### Можно и нужно сохранять как полноценную иерархию
- КС-2 работы;
- разделы;
- строки работ;
- суммы по разделам.

### Нужно рассматривать как "сжатие Excel в XML"
- удержания;
- требования;
- документы-основания удержаний;
- остатки аванса по периодам.

Иными словами:
- **Excel-модель удержаний** может оставаться богатой и иерархической;
- **XML-модель удержаний** будет компактной и агрегированной.

---

## 6. Что можно сделать дальше

### Вариант A — оставить богатую Excel-модель + честный compact XML

Это текущий pragmatic-путь:
- в UI храним все подпункты/документы/остатки;
- в XML отдаем:
  - итоговые суммы,
  - выбранный `ВидТреб`/`ВидУдерж`,
  - один документ-подтверждение,
  - агрегированную сумму `СумТребУдерж`.

### Вариант B — делать рядом "бизнес-preview → XML-preview"

Самый понятный для пользователя режим:
- сверху — полная Excel-таблица удержаний;
- снизу — отдельный preview, во что это реально схлопнется в `СвОРасч`.

### Вариант C — искать richer / альтернативный профиль выгрузки

Это уже исследовательская задача:
- проверить, можно ли в другом профиле / инстансе / внешнем контуре безопасно передавать несколько `УчетТребУдерж`;
- но в текущем рабочем профиле это уже отмечено как риск / ломает XSD.

---

## 7. Итог в одной фразе

**Иерархию работ — да, иерархию удержаний как в Excel — нет; для удержаний XML 1110335 требует сжатия модели.**
