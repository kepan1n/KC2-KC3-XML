# Сводка по комплекту XML-файлов: подрядчик / заказчик

Цель: зафиксировать, как из текущей формы должен собираться полный комплект XML, исходя из уже найденных XSD.

## 1. Что найдено

В каталоге `XSD__DOCS_FORMS_37783-KS-3` есть две отдельные XSD-схемы:

1. `ON_AKTREZRABP.xsd`
   - файл информации подрядчика
   - содержит:
     - `СвАктСдПр`
     - `НаимИСт`
     - `СвОРасч`
     - `ВсегоАктОтч`
     - `ПодписантПодр`

2. `ON_AKTREZRABZ.xsd`
   - файл информации заказчика
   - содержит:
     - `ПодписантЗак`
   - не содержит подрядческую табличную часть `НаимИСт`
   - не содержит `СвОРасч`
   - не содержит `ВсегоАктОтч` подрядческого типа

## 2. Вывод по архитектуре

Текущий генератор, который у нас уже есть и проверен в Контуре, — это **подрядческий файл** (`...P`).

То есть он покрывает:
- табличную часть КС-2;
- разделы и строки работ;
- сводные суммы;
- удержания;
- подрядческого подписанта.

Отдельные подписи заказчика не должны насильно встраиваться в подрядческий XML, потому что для них формат предусматривает **отдельный файл заказчика** (`...Z`).

## 3. Что нам нужно уметь генерировать

Принятое целевое решение:

### Файл 1 — XML подрядчика (`...P`)
Назначение:
- основной production-full XML по подрядчику;
- строится из формы;
- может генерироваться **по каждому листу КС-2**.

Что уже есть:
- production-full генератор;
- XSD-pass;
- проверка в Контуре без замечаний на small sample.

### Файл 2 — XML заказчика (`...Z`)
Назначение:
- отдельный XML со стороны заказчика;
- по структуре Контура соответствует **КС-3**;
- туда должны попасть заказческие подписи и роль заказчика как подписанта.

Что нужно сделать:
- спроектировать генератор `...Z`;
- решить, кто в нашей форме является `ПодписантЗак`;
- маппить туда подписи заказчика/техзаказчика.

### Уточнение по КС-3
- отдельный третий XML-файл для КС-3 в текущем комплекте **не нужен**;
- данные КС-3 должны использоваться внутри общего комплекта из двух файлов там, где это предусмотрено форматом.

## 4. Практическая стратегия реализации

### Этап А — закрепить текущий `...P`
- оставить как production-full основу;
- научить генерировать его по каждому листу КС-2, если листов несколько.

### Этап Б — сделать каркас `...Z`
- минимальный корректный XML заказчика;
- `ПодписантЗак`;
- базовые реквизиты и ссылка на тот же документ/акт.

### Этап В — отдельно проработать КС-3
- поднять данные из Excel КС-3 максимально как есть;
- затем определить, должна ли эта табличная часть жить:
  - в отдельном XML,
  - в одном из уже найденных файлов,
  - или в дополнительной экспортной форме комплекта.

## 5. Как трактуем текущую форму

Текущая веб-форма уже содержит всё, что нужно для такого комплекта:
- общая шапка документа;
- один или несколько листов КС-2;
- лист КС-3;
- удержания;
- подписи подрядчика;
- подписи заказчика / техзаказчика.

То есть форма уже является общим источником данных, а дальше задача — корректно разложить эти данные по нескольким XML-файлам комплекта.

## 6. Что делать следующим шагом

1. Не трогая уже рабочий `...P`, добавить поддержку **нескольких КС-2**.
2. Затем начать **генератор `...Z`**.
3. Данные КС-3 использовать внутри этой двухфайловой схемы там, где это предусмотрено форматом.

## 7. Короткий вывод

Система не должна ограничиваться одним XML-файлом.

Правильная цель:
- **комплект из двух XML-документов**,
- где текущий production-full XML подрядчика — это уже почти готовая первая часть,
- а следующим шагом нужно довести XML заказчика.
